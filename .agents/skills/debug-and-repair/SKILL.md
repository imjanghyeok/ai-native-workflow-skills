# 재현에서 원인 수정으로

## 계약과 기준 결과

원본 요구사항·적용되는 지침·실행 명령·관련 코드·기존 테스트·사용자 변경을 확인한다. 실행 가능한 경우 제품 코드 수정 전에 관련 기존 테스트와 실패 입력을 실행하고 기대/실제/종료 상태를 기록한다. 재현 불가면 보고된 증상과 관찰 사실을 구분하고 필요한 최소 추가 입력을 묻는다. 실행 환경을 고치느라 프로젝트 스택을 바꾸거나 모든 의존성을 갱신하지 않는다.

원문의 완료 조건과 기존 테스트가 다르면 양쪽 출처와 충돌 해소 근거를 남긴다. 테스트 통과만으로 동작이 올바르다고 판단하지 않는다. 분석만 요청받았으면 원인 후보와 검증 계획까지 남기고 제품 코드는 수정하지 않는다.

## 원인을 좁히는 루프

1. 입력 → 파싱/검증 → 업무 처리 → 저장/외부 응답 → 표시 중 최초로 계약이 깨지는 위치를 찾는다. 오류 로그가 마지막에 나온 위치가 원인 위치와 같다고 단정하지 않는다.
2. 관찰 근거가 있는 소수 가설을 만들고 각 가설을 구분할 작은 입력·명령을 선택한다. 가설을 검증 사실로 쓰지 않는다. 무작위 수정이나 같은 실패 명령의 반복보다 새 근거를 얻는다.
3. 상태·시간·순서에 의존하는 경우 실행 조건을 명시한다. 재시도·동일 시각·동률·순서 변경·실패 후 복구 중 관련 위험을 고른다.
4. 수정이 허용되었다면 원인에 가장 가까운 작은 변경을 한다. 예외 무시, 실패 결과를 성공으로 표시, 테스트 삭제, 무조건 재시도로 증상을 감추지 않는다. 기존 공개 계약과 관계없는 코드는 보존한다.
5. 실패를 잡는 회귀 검증이 수정 전 실패하고 수정 후 성공하는지 가능하면 확인한다. 관련 기존 테스트·인접 정상 흐름도 검증하고 환경 제약은 그대로 기록한다.

기존 프로젝트 컨벤션과 실제 검사 명령을 먼저 따른다. 일반 구현까지 이어갈 때는 사용 가능한 implement-and-verify 절차를 활용하되 다른 스킬 설치를 전제로 하지 않는다.

## 인계할 근거

기존 검증 문서에 증상·재현 입력/명령·원인·변경 위치·기존 계약 영향·실제 회귀 결과·남은 한계를 연결한다. 원인 추정만 있으면 ‘해결됨’이라고 보고하지 않는다. 외부 시스템 장애·성능 개선은 로컬 성공만으로 전체 해결을 주장하지 않는다.
