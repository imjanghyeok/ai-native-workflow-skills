# 요구에서 작은 검증 묶음 고르기

모든 과제에 같은 테스트 목록을 적용하지 않는다. 원문 완료 조건과 가장 실패 위험이 큰 부분에서 검증을 고른다.

| 확인할 성질 | 적절한 근거 |
| --- | --- |
| 계산·파싱·분기 규칙 | 작은 원본 입력과 독립 기대값 |
| 기존 오류 해결 | 수정 전 실패·수정 후 성공하는 회귀 |
| 입력→결과의 전체 연결 | 실제 CLI/API 또는 허용된 수동 웹 흐름 |
| 영속 저장 | 실제 저장 후 재읽기·요구된 재시작/새로고침 |
| 순서 무관·중복 정책 | 입력 재배치·동일 요청 반복 등 계약을 보존하는 변형 입력 |
| 제약 준수 | 결과에서 선행관계·충돌·가능 자원을 직접 검사 |
| 정확도·최적성 | 작은 수동/완전탐색 기준과 비교; 목표값·미해결 한계 |

## 피할 근거

- 구현과 같은 식을 테스트에서 그대로 복사하고 독립 기대값이라고 부르기.
- 서버 시작·화면 렌더·모의 응답 성공만으로 업무 완료를 주장하기.
- 모든 검사 생략·실패 숨김·기대값 낮추기로 통과시키기.
- 표본 1개 통과를 전체 데이터·성능·동시성 보장으로 확대하기.

정상 하나와, 결과를 크게 망칠 관련 실패/경계 사례부터 고른다. 이미 실행한 결과가 현재 변경에도 유효하면 재사용한다. 새 변경·새 실패·미확인 위험이 있을 때 범위를 넓힌다. 제공 도구가 없으면 임의의 통과를 쓰지 말고 미실행 사유와 가능한 대체 확인을 기록한다.

## 제출 직전

원문 요구 ID → 구현 위치 → 실제 검증 → 남은 한계를 연결한다. 제출 파일이 실제 존재하고 입력 경로·의존성·실행 명령·실제 사용 포트가 안내와 일치하는지 본다. 다른 사람이 재현할 최소 명령을 남긴다. 필수 미완료는 미완료라고 표시한다. 최종 제출 확정은 실제 사용자 요청과 환경 절차를 따른다.
