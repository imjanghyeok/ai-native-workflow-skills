# API·저장·재시도 과제 점검

실제 계약에 관련된 항목만 고른다. 인증·DB·외부 API가 제공된다고 가정하지 않는다.

## 입력과 기존 계약

호출 경로·메서드·스키마·상태 코드·오류 형식·호출부를 확인한다. 값 누락/타입/범위/빈 결과/중복 요청을 계약대로 처리한다. 서버 예외를 성공 응답으로 감추지 않는다. 페이지 조회는 안정적 정렬과 동률 키, 페이지 사이 중복/누락을 확인하고 날짜 범위의 포함 여부·시간대를 명시한다.

## 상태 변경

어디에 저장되는지와 성공 시점을 확인한다. 화면의 성공 알림이 실제 저장을 보장하지 않는다. DB·파일 등 실제 저장 경로를 다시 읽고, 실패 시 이전 상태와 부분 반영 여부를 검사한다. 저장 형식과 데이터 이동은 기존 구조를 따른다. 인메모리 처리를 영속 저장이라고 설명하지 않는다.

## 재시도와 중복

같은 요청의 식별 기준·중복 허용 여부·동시 요청·실패 후 재시도 계약을 먼저 확인한다. 단순 조회 후 삽입은 동시에 들어올 때 중복을 막지 못할 수 있다. 저장소가 지원하는 유일성·원자적 처리·트랜잭션이 필요한 범위를 검토한다. 요청 키가 같지만 내용이 다를 때를 임의로 같은 요청으로 처리하지 않는다.

외부 효과와 내부 저장이 엇갈리는 실패를 따로 본다. 예: 외부 작업 성공 후 내부 저장 실패, 내부 상태 기록 후 외부 작업 실패. 무조건 재시도해서 외부 효과가 반복되는지 확인한다. 분산 트랜잭션이나 exactly-once를 근거 없이 보장하지 않는다. 외부 제공 기능이 없으면 재현 가능한 대체 경계와 미확인 범위를 명시한다.

## 실제 검증

핵심 정상 요청, 같은 요청 반복, 충돌 요청, 실제 요구의 실패 단계와 회복 경로를 테스트한다. 동시성 보장을 주장하려면 그에 맞는 검증과 저장 규칙 근거가 필요하다. 모의 외부 호출 테스트와 실제 연결 성공을 구분한다. 비밀값을 출력하거나 코드에 하드코딩하지 않는다.
