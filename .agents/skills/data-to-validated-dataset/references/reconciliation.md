# 가공 결과를 원본과 대조하는 법

처리 코드 실행 성공은 데이터 정확성의 근거 중 일부다. 업무 단위와 기대되는 변화가 맞는지 별도로 확인한다.

## 관련 있는 점검만 선택

| 단계 | 대조 근거 | 실패를 드러내는 예 |
| --- | --- | --- |
| 추출 | 읽은 범위, 원본/추출 건수, 필수 열·타입·단위, 원본 위치별 값 | 표 두 열이 합쳐짐, 음수 기호 누락, 헤더/합계가 데이터로 포함 |
| 행 검증 | 입력 = 채택 + 제외라는 관계가 적용되는 단계와 제외 이유별 건수 | 파싱 실패 행이 집계에서도 오류 기록에서도 빠짐 |
| 중복 처리 | 정상 입력에서 대표·추가 중복·상충으로 제외된 행이 어떻게 나뉘는지 | 마지막 상충 기록 전 누적값이 남음, 제외 사유가 겹쳐 이중 계산 |
| 결합 | 키 유일성, 매칭·미매칭, 결합 전후 행 수, 기준 수량 보존 | A 수량 100이 B의 두 로그와 연결되어 합계 200으로 늘어남 |
| 집계 | 합계의 합계, 분자·분모, 고유 대상 수, 0 분모 | 일별 1/10과 10/1000을 단순 평균해 5.5%로 표시: 전체 비율은 11/1010 |
| 저장 | 출력 재읽기, 스키마·타입·인코딩, 재실행 결과, 원본 불변 | ID 0012가 12로 변함, null이 문자열로 저장, 재실행마다 행 누적 |

여기서 ‘건수’는 행·고유 ID·사건·출력 그룹 중 무엇인지 명시한다. 하나의 원본 행이 여러 결과로 나뉘는 추출, 1:N 결합이나 집계에서는 단순 행 수 일치가 정답이 아니다. 중첩되는 오류가 있으면 상호 배타적으로 셀 것인지 중복 표시할 것인지 기록한다.

유효성·중복 처리 이후의 미매칭은 별도 단계로 센다. 예를 들어 raw=invalid+duplicate+conflict+accepted와 accepted=matched+unmatched를 함께 쓰며, 충돌 ID 개수와 제외 행 개수를 혼합하지 않는다. 결합 기준에서 제외되는 유효 수량도 따로 보존해 매칭+미매칭 합계와 원본 채택 합계를 대조한다.

수치 범위가 관련 위험이면 정상 크기뿐 아니라 표현 경계와 합계 경계를 원본의 정확한 값으로 대조한다. 손실된 같은 런타임 숫자로 기대값을 만들면 잘못된 값끼리 같아질 수 있다. 출력은 필요한 필수 키·ID·null·원본 위치·기록/해시 구조까지 확인하며 JSON 파싱 성공만을 전체 스키마 검증으로 삼지 않는다.

## 독립적인 작은 검증

요구에 관련된 2~5행을 직접 추적해 기대값을 만든다. 예를 들어 생산 `(id=A, 수량=100)`과 알람 `(A, 코드=X), (A, 코드=Y)`가 결합되어도 생산 총량은 업무 계약상 100인지, 알람별 출력에서 의도적으로 반복하는 것인지 확인한다. 결합 결과가 두 행이라는 사실만으로 생산 합계 200을 정당화하지 않는다.

순서에 무관해야 하는 변환은 입력을 바꿔도 같은 의미의 결과인지 확인한다. 상충 ID·미매칭·0/null·빈 입력·파싱 실패 중 실제 요구의 위험을 고른다. 모든 과제에 모든 오류 유형을 의무화하지 않는다.

## 짧은 기록 형식

기존 문서에 다음을 담으면 된다. 별도 보고서나 산출물 파일명을 강제하지 않는다.

- 원본 식별: 파일/시트/범위, 필요한 경우 파일 해시, 읽은 범위와 전체/표본 여부.
- 계약: 한 행의 의미, 키·타입·단위·기간·시간대, 요구 ID와 정책 근거.
- 변환: 단계별 규칙, 가정·제외·상충·미매칭 처리, 출력 위치.
- 검증: 실제 명령과 입력, 원본 기반 기대값, 관찰값, 상태, 출처 위치.
- 한계: 읽지 않은 범위, 추출 도구 부재, 문서 대조 범위, 성능·숫자 정밀도 미확인.
