# 설계를 코드와 실행 근거로 연결하기

사용자가 구현을 요청한 범위에서 동작하는 결과물을 만들고, 실제 수행한 검증만 근거로 남긴다. 특정 언어·프레임워크·MCP에 의존하지 않는다.

## 착수

- 원본 README, 기존 지침, 관련 요구사항·설계, 현재 코드를 읽는다. 문서가 부족하면 필요한 결정과 미정 사항을 먼저 정리한다. 다른 스킬이 반드시 설치되어 있어야 한다고 가정하지 않는다.
- 실행 명령·의존성·제출 파일·응답 계약을 확인한다. 기존 코드와 사용자 변경을 보존하며 요구에 필요한 부분을 고친다. 현재 언어·구조를 불필요하게 교체하지 않는다.
- 저장소·도구에서 허용된 기능만 사용한다. 외부 모델·새 MCP·계정·배포를 임의로 추가하지 않는다. 기존 Codex와 터미널로 작업이 끝나면 그대로 진행한다.

## 코드 작성 컨벤션

이 준비 묶음의 새 프로젝트 기본값은 [JavaScript/TypeScript 작업 프로필](references/js-stack.md)을 참고한다. 실제 과제 스택이 우선이며 기존 프로젝트를 바꾸는 근거로 쓰지 않는다. 설치 없는 연결 예제가 필요할 때만 [JS 시작본](assets/js-starter/README.md)을 필요한 범위에 복사·병합한다. 기존 파일 삭제·전체 덮어쓰기를 전제로 하지 않는다.

첫 제품 코드 변경 전에 [컨벤션 발견·적용 가이드](references/conventions.md)를 읽는다. 적용되는 지침, 실제 도구 설정과 주변 대표 코드에서 규칙을 찾아 구현에 반영한다. 현재 프로젝트 규칙을 우선하고, 없는 규칙만 언어에 맞는 최소 기본값으로 선택한다. 필요한 규칙·출처·검증 명령을 기존 설계 또는 작업 설명에 짧게 남긴 뒤 구현을 진행한다.

컨벤션 문서를 만들었다는 사실로 준수를 판단하지 않는다. 변경 diff와 실제 검사 결과까지 확인한다.

## 문법·표준 기능이 불확실할 때

[작업별 문법 레시피 가이드](references/language-recipes.md)에 따라 실제 프로젝트 언어·버전에 맞는 작은 예제로 확인한다. 기존 구현과 표준 기능을 먼저 살피고, 필요한 경우 허용된 공식 자료를 확인한다. 자료구조·알고리즘의 선택 이유가 미정이면 입력 규모·업무 규칙으로 판단하고 설계에 남긴다. 다른 스킬 설치나 별도 MCP를 필수 조건으로 만들지 않는다.

## 작업 루프

과제에 관련된 가이드만 읽는다: [API·저장·재시도](references/api-and-state.md), [웹 업무 흐름](references/web-flow.md), [검증 선택·제출 점검](references/test-selection.md). 일반 참고 목록을 새 필수 기능이나 추가 인프라 요구로 해석하지 않는다.

기존 코드 수정 과제에서는 제품 코드 변경 전에 관련 기존 테스트와 대표 입력을 실행해 기준 결과를 남긴다. 기존 테스트 통과만으로 요구 충족을 판단하지 말고 원문 완료 기준과 대조한다. 요구와 충돌하는 테스트를 수정할 때는 양쪽 출처와 기대값 변경 근거를 남긴다. 가능하면 문제를 드러내는 회귀 검증이 수정 전 실패하고 수정 후 성공하는지 확인한다. 실행이 불가능하면 그 이유와 미확인 상태를 기록한다. 새 프로젝트에는 존재하지 않는 기준 실행을 만들지 않는다.

1. 다음에 충족할 R-ID와 기대 결과를 정한다. 기존 오류 수정이면 먼저 실제 재현 여부와 입력을 확인한다.
2. 작은 변경을 구현하고 변경 내용을 읽는다. 코드에 없는 성질을 요약만 보고 가정하지 않는다. AI가 선택한 정책과 사용자의 업무 결정을 구분한다.
3. 그 변경을 검증할 실제 명령을 실행한다. 기존 테스트와 요구에 맞는 정상·경계·실패 입력을 고른다. 서버가 시작됐다는 사실과 업무 흐름이 완료됐다는 사실은 별개로 확인한다.
4. 실패하면 입력·오류·관찰 결과를 근거로 원인을 좁혀 수정한다. 기대값을 구현에 맞춰 낮추거나 실패한 테스트를 제거해 통과시키지 않는다.
5. 요구 변경이나 설계 수정이 생기면 관련 문서와 검증 기준을 함께 갱신한다. 끝난 요구와 미완료 요구를 구분한다.

## 결과물

[검증 근거 규약](references/evidence.md)을 참고해 기존 제출 양식 또는 `docs/verification.md`에 기록한다. 실행한 명령, 입력, 기대값, 실제값·종료 상태, 관련 파일·요구 ID, 남은 한계를 남긴다. 전체 로그를 무조건 복사하지 말고 재현 가능한 근거를 선택한다.

설명 준비에는 ‘선택한 것 → 이유 → 코드·실행 근거 → 한계’를 사용한다. 다음에 확인할 질문은 만들 수 있지만 실제 시험에서 본인이 직접 답해야 하는 답변을 대신 제출하거나, 수행하지 않은 판단·검증을 본인 활동으로 만들어내지 않는다.

검증 완료 후 필요한 제출 파일과 실행 안내가 실제 저장되어 있는지 확인한다. 플랫폼 제출 확정·외부 전송은 사용자 요청과 실제 환경 절차에 따른다.
