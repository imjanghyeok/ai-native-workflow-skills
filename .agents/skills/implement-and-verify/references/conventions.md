# 프로젝트 컨벤션을 발견하고 구현에 적용하기

코딩 스타일을 미리 고정하지 말고 수정 대상 프로젝트의 규칙부터 확인한다. 컨벤션은 표기뿐 아니라 파일 배치, 인터페이스, 오류 처리, 데이터·상태 흐름, 검증 방식까지 포함한다.

## 1. 변경 범위에서 규칙 찾기

다음은 발견 후보이며 전부 존재하거나 읽어야 하는 필수 파일 목록이 아니다. 관련 범위부터 확인하고 대용량·생성 파일·의존성 폴더를 무작정 탐색하지 않는다.

| 근거 | 확인할 것 |
| --- | --- |
| 적용되는 AGENTS.md, README, CONTRIBUTING, 제출 안내 | 파일별 작업 규칙, 수정 금지 영역, 필수 명령, 기존 계약 |
| .editorconfig, .gitattributes | 들여쓰기·줄바꿈·인코딩 규칙 |
| package.json, 잠금 파일, ESLint·Prettier·Biome·tsconfig 설정 | 사용 런타임·패키지 관리자, 실행 스크립트, 타입·포맷·검사 규칙 |
| pyproject.toml, Ruff·Black·mypy·pytest 설정, requirements·잠금 파일 | Python 버전·도구·명명·타입·테스트·의존성 규칙 |
| pom.xml, Gradle·Checkstyle·Spotless 설정 등 | 해당 언어의 빌드·포맷·검사 방식 |
| 수정 대상 주변의 대표 구현과 테스트 | 파일 배치, 이름, 책임 분리, 오류·로그·반환 형식, 테스트 패턴 |

같은 역할의 최근 구현 1~3개와 관련 테스트 정도부터 확인한다. 저장소 전체를 다시 분석할 필요는 없다. 빌드·포맷 설정이 상속·확장되면 실제 적용되는 설정을 확인한다.

규칙 간 충돌은 적용 범위와 사용자 지시를 확인해 해소한다. 오래된 파일 하나의 스타일을 도구 설정보다 우선하는 규칙으로 일반화하지 않는다. 명시적인 요구가 기존 관례와 다르면 요구와 변경 영향을 기록한다. 영향이 작은 명명·서식 선택 때문에 매번 질문하지 않는다.

## 2. 구현에 사용할 최소 규칙표

첫 수정 전에 다음 중 관련 있는 항목을 출처와 함께 짧게 정리한다. 기존 설계 문서가 있으면 ‘구현 규칙’ 절에 덧붙이고, 작은 변경은 작업 설명에 남긴다. 별도 규칙 문서를 매번 새로 만들지는 않는다.

- 언어·버전 / 실행·패키지 관리자 / 사용할 기존 명령
- 파일 위치·모듈 경계 / 함수·변수·파일 명명 / 들여쓰기·따옴표 등 도구가 정하는 서식
- 외부 입력의 검증 위치 / 타입·스키마 / 응답·오류 형식 / 상태 변경·저장 책임
- 테스트 위치·이름 / 기존 fixture·mock 방식 / 변경에 필요한 검증 명령
- 명시된 규칙 / 주변 코드에서 관찰한 관례 / 규칙이 없어 선택한 기본값

예: ‘API 오류는 errors.py의 DomainError → handler에서 응답으로 변환한다. 출처: 해당 파일·함수’처럼 실제 확인한 내용을 적는다. 이 예시의 클래스나 파일을 새 프로젝트에 의무적으로 만들지 않는다.

## 3. 코드 작성 시 지킬 경계

- 기존 공개 함수·API·스키마·CLI 입출력을 유지한다. 요청된 변경으로 계약을 바꾸는 경우에는 호출부·테스트·실행 안내도 함께 맞춘다.
- 책임이 맞는 기존 모듈·도우미를 활용하고 같은 규칙을 중복 구현하지 않는다. 재사용할 실제 수요가 없는 추상화·계층은 추가하지 않는다.
- 데이터 파싱·단위·시간대·널 처리·오류 변환은 기존 경계를 따른다. 프런트엔드 표시만 바꾸어 서버 실패를 성공처럼 감추지 않는다.
- 타입·입력 검증은 프로젝트의 방식과 요구에 맞춘다. 타입 우회, 무분별한 any, 광범위한 예외 무시, 의미 없는 기본값으로 실제 오류를 덮지 않는다.
- 주석은 코드에서 바로 보이지 않는 업무 이유·제약을 설명한다. 함수명이나 한 줄 코드를 그대로 번역한 주석을 늘리지 않는다.
- 테스트는 관찰 가능한 요구와 실패 위험을 검증한다. 구현 세부를 그대로 복제하는 검사나 근거 없는 임계값을 추가하지 않는다.
- 필요한 변경에 집중한다. 관계없는 파일 재정렬·전체 포맷·공통 구조 교체·잠금 파일 갱신을 섞지 않는다. 필요한 의존성 변경은 기존 관리자와 버전 정책을 따른다.

## 4. 규칙이 없거나 새 프로젝트인 경우

언어와 작업 유형이 정해진 뒤 단순한 기본값을 골라 밝힌다. 특정 언어·프레임워크·패키지 관리자를 모든 과제에 강제하지 않는다.

- 읽기 쉬운 이름, 작은 책임 단위, 일관된 파일 배치를 사용한다.
- 같은 개념에는 같은 이름을 쓰고 의미 있는 상수·입출력 구조를 사용한다.
- 명명은 언어의 일반적인 관례를 따른다. 예를 들어 Python 함수 snake_case와 JS/TS 함수 camelCase는 언어에 맞춘 선택의 예다.
- 이미 제공된 도구가 있으면 활용한다. 컨벤션을 맞춘다는 이유만으로 새 포맷터·린터·무거운 의존성을 설치하지 않는다.
- 제출·실행에 필요한 최소 구조부터 만들고, 프로젝트 크기에 맞게 분리한다.

## 5. 구현 후 확인

변경 diff에서 규칙표와 실제 코드가 맞는지 확인한다. 발견한 명령을 그대로 추측하지 말고 스크립트·설정에 존재하는지 확인한다. 프로젝트가 요구하는 포맷·타입·린트·테스트 중 변경에 해당하는 검사를 수행하고, 도구·환경이 없어 실행하지 못한 항목은 미확인으로 남긴다. 자동 수정은 의도한 파일 범위로 제한한다. 더 넓은 검사가 필수이면 실행하고 관계없는 변경이 섞이지 않았는지 확인한다.

최종 기록에는 ‘적용한 주요 규칙과 출처 / 실행한 검사와 실제 결과 / 남은 위반·예외·미확인’을 간단히 남긴다. 명령을 제안한 것과 실행해 통과한 것을 구분한다.
