# 아키텍처와 의존성의 근거

설계 그림의 모양을 먼저 정하지 않는다. 실제 코드·실행 설정으로 다음 층을 구별한다.

| 관점 | 확인할 근거 | 피할 혼동 |
| --- | --- | --- |
| 시스템 경계 | 사용자 입력·파일·외부 API·배포 설명 | 외부 서비스를 제공받았다고 가정 |
| 실행 단위 | 실제 시작 명령·빌드·프로세스·포트·컨테이너 설정 | 논리 레이어를 별도 서버로 표시 |
| 모듈/객체 | import/export·인스턴스 생성·함수 호출·상태 접근 | 클래스가 없는 코드를 임의 OOP로 설명 |
| 데이터 소유 | 스키마·repository·파일 경로·쓰기 호출·트랜잭션 | 화면 상태와 영구 저장을 동일시 |
| 보안 경계 | 주체 확인·서버 인가·리소스 소유 검사·설정 | UI 버튼 숨김을 권한 통제로 간주 |
| 배포/운영 | 환경 변수·마운트·DB 연결·로그·상태 검사 | 로컬 시작을 클라우드 배포 성공으로 보고 |

의존성은 파일 이름만 열거하지 말고 `무엇이 없으면 어떤 기능이 실패하는가`까지 잇는다.

- manifest는 선언 범위, lock은 해석된 버전, 설치 목록은 현재 설치 상태다. 서로 구분하고 실제 근거가 없으면 미확인으로 둔다. 프런트 번들과 서버 런타임의 포함 관계도 따로 확인한다.
- 직접 import와 전이 의존성, 타입/빌드 전용과 런타임, 내장 모듈과 외부 패키지를 구분한다. 기존 도구의 범위 좁힌 의존성 출력과 import 탐색을 활용하고 전체 node_modules를 읽지 않는다.
- 순환 의존·경계 역전·동일 규칙 중복을 발견하면 실제 경로와 영향으로 설명한다. `깔끔한 구조`라는 이유만으로 전면 재구성하지 않는다.
- 외부 서비스/환경 변수는 이름·용도·필수 여부·없을 때 실패·민감값 주입 방식을 기록한다. 값·토큰·연결 비밀은 문서에 넣지 않는다.
- 패키지/소스 채택은 용도·버전/커밋·라이선스·필요 파일·실행/네트워크·전이 의존성·대안·변경 범위를 확인한다. 출처 라이선스만으로 모든 전이 의존성 사용을 검증했다고 쓰지 않는다.
- 상태 변경, 비동기 작업, 동시 요청, 캐시가 실제로 있으면 일관성·실패·재시도 책임도 지도에 표시한다.

필요한 그림은 문맥/실행 단위 flowchart, 모듈 의존 flowchart, 호출 sequence, 데이터 erDiagram 중 선택한다. C4 도구나 새로운 아키텍처 프레임워크 설치는 필수가 아니다. 구조가 작으면 한 그림과 한 표로 충분하다.
