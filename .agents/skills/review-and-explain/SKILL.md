# 구현·판단·설명을 실제 근거와 대조하기

검토할 원문·파일 집합/상태·실제 명령/출력을 확인한다. 다른 세션이 읽기 전용으로 검토하면 별도 세션 리뷰, 같은 대화 역할 전환이면 자기 점검이다. 이름만 reviewer인 것을 독립 평가로 부르지 않는다.

읽기 전용 검토에서 원본 과제 README·AGENTS·입력·코드·테스트는 수정하지 않는다. 출력 문서 경로를 명확히 하고, 지적을 설명하기 위해 원문 요구를 보충/재작성하지 않는다. 원본 해시가 바뀌면 알려서 출력 범위를 바로잡고 검토 기준이 달라진 사실을 남긴다.

## 리뷰 결과

요구 충족 → 데이터/권한/실패·저장 → 프런트/서버 통합 → 배포 준비·의존성 → 코드 컨벤션·문서 일치 순으로 필요한 범위만 살핀다. 모든 일반 보안/성능 항목을 새 필수조건으로 만들지 않는다. 보고할 지적에는 심각도·실제 파일/심볼·원문 계약·재현/정적 근거·영향·수정 방향을 붙인다.

제품 코드는 읽기 전용으로 보고 지적을 해당 소유자에게 인계한다. 테스트를 실행하려면 출력 파일 등 쓰기 범위를 확인하고 필요하면 격리된 임시 출력으로 검증한다. 리뷰 중 코드가 바뀌면 기준 snapshot을 갱신해 관련 경로만 다시 확인한다. 전체 검토가 불가능하면 확인 범위를 적는다.

확정된 요구 위반과 미정 정책을 구별한다. 읽기 전용 리뷰에서 고치지 않았다고 해서 명확한 요구를 새 사용자 판단 사항으로 바꾸지 않는다. 단순 오류 표시 문구 같은 기술적 재량과 업무 정책 선택도 분리한다.

[리뷰 수용 기준](references/review-reception.md)에 따라 확인된 결함/요구 해석 차이/방어 보완/선호를 구별한다. 사용자 제안과 AI 리뷰 모두 원문·코드·실행 근거로 검토하며 자동 채택하거나 형식적으로 반대하지 않는다. 제안→채택/수정 채택/거절/보류→실제 변경→재검증을 결정 ID로 연결한다.

## 문서와 실행의 일치

- 테스트 수·성공/실패·명령·기준 코드 상태를 최종 로그와 대조한다. 중간 실행의 실제 이력은 보존하고 최종 요약과 구분한다.
- 코드맵의 파일·API·의존성·권한·저장 화살표를 실제 코드로 확인한다. 계획/정적 관찰/실행 확인/미확인을 섞지 않는다.
- UI mock, 시작본 성공, 서버 시작, 부분 테스트 통과를 업무 완료로 대신하지 않는다. 원문 명령 실패는 그대로 공개한다.

주요 기능별로 구현 위치/책임·사용 순서·실제로 수행한 확인 방법과 결과가 연결되는지 [기능 근거 표](../code-to-system-map/references/flows-and-evidence.md)로 대조한다. 서버 시작/HTTP 성공만 확인하고 사용자의 화면 확인까지 했다고 쓰지 않는다. 새 문항/답안집 대신 실제 현재 코드/실행 근거의 연결을 작업 단계에서 남긴다.

## 이해 확인

실제 코드맵과 결정 기록에서 요청 경로·모듈 책임·의존성 장애·선택한 방식의 장단점·거절 대안·미검증을 묻는다. 사용자의 설명에서 근거 없는 주장·틀린 위치·빠진 실패 경로를 실제 코드·결과와 연결해 보완한다. 사용자가 답하기 전 AI가 쓴 설명을 사용자 이해나 본인 판단으로 기록하지 않는다.

연습 자료는 작성할 수 있지만 실제 후속 서술형에서 AI/복사·붙여넣기가 금지되면 그 단계의 답변 작성에 사용하지 않는다. 이해 자료의 존재는 전 코드 이해의 증명이 아니다.

운영안/추천이 제출물일 때는 [운영안 비교](../optimize-and-compare-plans/SKILL.md) 기준으로 같은 입력·평가기에서 필수 제약·누락 수요·목적값·기준안·절충/불확실성을 대조한다. 시간 초과를 불가능 증명으로, 근사 후보를 전역 최적해로 바꾸지 않는다.
