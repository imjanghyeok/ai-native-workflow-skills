# 검증과 설명에 남길 근거

검증 표의 최소 열: 검증 ID | 요구 ID | 명령·입력 | 기대 결과의 출처 | 실제 관찰 | 상태 | 관련 코드.

상태는 ‘성공 / 실패 / 미실행 / 환경 제약으로 확인 불가’를 구분한다. 계획한 테스트를 실행한 테스트로 적지 않는다. 함수 테스트, API 요청, 웹 화면 확인, 영속성 확인은 각각 실제 수행한 범위로 기록한다.

- 단위: 규칙의 계산·분기·상태를 작은 입력으로 확인한다.
- 통합: 입력부터 결과 반환/저장까지 실제로 이어지는지 확인한다.
- 회귀: 수정과 인접한 기존 계약이 유지되는지 확인한다.
- 실패: 원문에 관련된 잘못된 입력·저장 실패·타임아웃·중복 등의 관찰 가능한 처리를 확인한다.

선택적으로 적용하며 모든 과제에 모든 테스트 종류를 의무화하지 않는다. 가장 위험한 요구를 먼저 검증하고 실행 자원·시간을 고려한다.

설명 메모는 짧게 작성한다:
1. 어떤 모호함을 어떻게 처리했고 그 결정의 출처는 무엇인가?
2. 실제 바뀐 파일·함수·동작은 무엇인가?
3. 어떤 입력에서 기대와 실제가 일치/불일치했는가?
4. 확인하지 못한 범위와 다음 검증은 무엇인가?

AI 대화 기록이 없으면 누가 어떤 수정을 했는지 단정하지 않는다. 기록과 코드가 맞지 않으면 답변을 꾸미지 말고 그 불일치를 먼저 확인한다.
