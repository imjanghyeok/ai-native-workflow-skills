# 요구사항을 구현 가능한 설계로 연결하기

요구사항의 ID·출처를 설계 결정과 검증 방법까지 이어 준다. 문서와 다이어그램은 구현을 돕는 만큼만 만든다.

## 근거부터 확인

- 사용자가 지정한 요구사항 문서와 원본 README를 읽고, 관련 코드·데이터·기존 테스트를 확인한다. 요구사항 문서가 없다면 원문에서 이 설계에 필요한 조건과 미정 사항을 먼저 추출한다. 다른 스킬 설치를 전제로 하지 않는다.
- 과제 안내와 원본 계약을 우선한다. 이전 분석 문서에 근거 없는 가정이 있으면 확정 조건으로 재사용하지 않는다.
- 기존 프로젝트의 언어·구조·인터페이스를 유지할 수 있는 가장 작은 변경을 우선 검토한다. 새 기술·외부 서비스·LLM API를 제공받았다고 가정하지 않는다.
- 불확실한 사항은 영향과 임시 가정을 표시한다. 핵심 판단을 막는 질문만 제시하고, 독립적으로 진행 가능한 설계는 계속한다. 이미 설계·개발이 허용된 작업에 일률적인 승인 단계를 추가하지 않는다.

## 자료구조·알고리즘 판단

집계·중복 처리·정렬·탐색·관계·스케줄처럼 자료 처리 방식의 선택이 필요한 경우 [선택 가이드](references/algorithm-choice.md)를 읽는다. 입력 크기와 업무 규칙에 맞춰 가장 단순한 후보를 고르고, 선택 이유·비용·정확성 한계·검증 입력을 설계에 연결한다. 모든 과제에 복잡한 알고리즘을 의무적으로 적용하지 않는다.

## 최소 설계

우선순위·작업 배정·스케줄·비용 최적화가 실제 요구라면 [제약과 기준안 가이드](references/constraints-and-ranking.md)를 읽어 필수 제약·목적·가정·실행 가능성 검증과 최적성 한계를 구분한다.

1. 필수 업무 흐름 하나를 입력 → 검증 → 처리 → 결과/오류로 끝까지 연결한다. 웹·API·분석·문서 과제에 맞는 실행 계약을 사용한다.
2. 바꿀 파일·함수·모듈과 책임, 데이터·상태의 소유자, 입출력, 실패 시 동작을 정한다. 실제 필요한 항목만 다룬다.
3. 재시도·동시성·중복·날짜·단위·결측·저장 같은 문제가 요구에 있으면 정책과 경계를 명시한다. 요구에 없는 복잡한 분산 구조를 추가하지 않는다.
4. 선택 이유와 중요한 대안 하나를 비교한다. 미정 정책에 의존하는 결정은 가정 ID와 연결한다. ‘최적’, ‘안전’, ‘정확’ 같은 보장은 검증 범위를 함께 적는다.
5. 필수 요구마다 변경 위치와 검증 입력·기대 결과를 연결한다. 정상 흐름 외에 해당 요구가 실패할 실제 경계·실패 입력을 고른다. 이 단계에서는 실행 결과를 ‘계획’으로 표시한다.
6. 한 번에 확인 가능한 작은 구현 단위로 순서를 잡는다. 실행 가능한 최소 흐름 → 필수 오류 처리 → 요구 기반 검증 → 제출·설명 정리 순서를 과제에 맞게 조정한다. 남은 시간이 알려졌으면 문서·구현·검증·제출에 배분하고 추정임을 밝힌다.

데이터 가공이 필요한 과제는 원본·중간·출력의 위치, 추출/정규화/결합/집계의 순서와 단위, 출처 추적을 설계에 포함한다. 결합 키의 관계와 행 증식 위험, 제외·중복·미매칭 건수 및 수량 합계를 어떻게 대조할지도 계획한다. 모든 가공에서 행 수가 보존된다고 가정하지 않는다.

## 다이어그램

[다이어그램 선택 기준](references/diagrams.md)을 필요할 때 읽는다. 핵심 흐름이 한눈에 보이는 Mermaid 다이어그램 하나부터 만든다. 데이터 관계나 호출 순서가 별도 그림으로 더 명확해질 때만 추가한다. 실제 존재하는 구조와 제안 구조를 구분한다. 렌더링 도구가 없다면 원문과 짧은 흐름 설명을 남기고, 렌더 검증을 했다고 쓰지 않는다.

## 결과물과 인계

기존 문서 위치를 따르며 없으면 `docs/design.md`에 목표·결정·다이어그램·추적 표·구현 순서를 작성한다. 원본 요구사항 전체를 복사하지 말고 ID로 참조한다. 검증 계획도 짧으면 같은 파일에 둔다.

분석/설계만 요청받았으면 여기까지 마무리한다. 구현까지 요청받았으면 이 설계를 따라 작업을 이어가고, 코드 변경으로 결정이 바뀌면 문서도 실제 구조에 맞춘다.
