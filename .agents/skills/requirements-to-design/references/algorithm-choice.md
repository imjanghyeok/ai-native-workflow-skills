# 요구에서 자료구조·알고리즘 선택하기

과제의 데이터 크기·요구 결과·업무 규칙을 먼저 확인한다. 알고리즘 이름을 맞히는 대신 ‘왜 이 구조가 필요한지, 어떤 입력에서 한계가 있는지’ 설명할 수 있는 선택을 만든다.

## 선택 전에 확인할 정보

- 입력 건수와 증가 폭, 메모리에 올릴 수 있는지, 일괄 처리인지 연속 입력인지.
- 중복·동일 시각·순서 변경·누락·동일 ID 충돌을 어떻게 처리해야 하는지.
- 출력 순서와 동률 처리, 조회/수정 빈도, 정확한 최적해가 필요한지.
- 데이터가 정렬되어 있는지, 관계가 순환할 수 있는지, 구간 끝점을 포함하는지.

크기를 모르면 가정이라고 표시하고, 현재 과제에 필요한 단순한 방법을 먼저 고른다. 정렬·인덱스·캐시를 넣기 전에 필요한 정확성을 확인한다.

## 상황별 선택표

| 상황 | 먼저 검토할 구조·방법 | 규칙·검증 포인트 |
| --- | --- | --- |
| ID별 조회, 항목 합치기 | Map/dict 기반 인덱스 | 동일 ID·서로 다른 내용의 충돌 정책, 누락 ID |
| 존재 여부·동일 항목 중복 제거 | Set 또는 키를 추출한 Map | 동일성을 ID로 볼지 전체 내용으로 볼지 먼저 결정 |
| 날짜·설비·제품별 집계 | 그룹 키 → 누적 상태 Map | 평균의 평균을 피하고 원래 분자·분모를 누적, 0 분모·단위 |
| 우선순위·날짜 순 목록 | 명시적인 복합 키 정렬 | 동률의 결정적 기준, 문자열과 숫자의 정렬 차이 |
| 상위 K개만 유지하는 반복 처리 | 크기 K 힙 또는 전체 정렬 | 전체 정렬이 충분히 단순한지 먼저 판단, 동률·K=0 |
| 시간 구간 묶기·알람 사건화 | 정렬 후 순회, 그룹별 상태 | 고정 구간/마지막 사건 기준, 경계 시각, 설비 간 분리 |
| 선입선출 작업·너비 우선 탐색 | 큐, 방문 집합 | 배열의 앞 제거 비용, 순환·중복 방문 |
| 연결 관계·선행 작업 | 인접 리스트 + DFS/BFS/위상 정렬 | 순환·단절·존재하지 않는 노드, 위상 순서는 자원 배정 최적화와 별개 |
| 정렬된 자료의 반복 범위 조회 | 이진 탐색·정렬 인덱스 | 정렬 비용, 비교 기준, 시작/끝 포함, 중복 키 |
| 누적 구간 합을 반복 조회 | 누적 합 | 업데이트가 잦으면 적합성 재검토, 빈 구간·인덱스 |

표는 첫 후보다. 기존 DB나 라이브러리가 필요한 정렬·집계·범위 조회를 이미 지원하면 그 기능을 우선 검토한다. 자료구조를 추가하기 위해 구조를 복잡하게 만들지 않는다.

## 비용과 정확성 설명

비교 정렬의 일반적인 선택은 O(n log n), 단일 순회는 O(n)이다. 해시 기반 조회·추가는 보통 기대 O(1)이지만 최악 보장이 아니라 구현·충돌 조건에 의존한다. 실제 사용하는 언어와 라이브러리의 보장을 확인한다.

‘한 번 순회’라도 내부에서 전체 배열을 다시 찾거나 정렬하면 전체 비용이 달라진다. 시간뿐 아니라 보관하는 인덱스·복사·정렬 버퍼의 메모리도 설명한다. 현재 입력에서 실행됐다는 사실만으로 대규모 입력의 성능을 보장하지 않는다.

탐욕법·휴리스틱은 정확한 최적해 보장과 구분한다. 예를 들어 위상 정렬은 선행 조건을 지키는 순서의 후보를 만들지만, 설비·점검·마감 제약까지 만족하는 최적 스케줄을 자동으로 보장하지 않는다.

## 설계에 남길 짧은 근거

요구 ID / 업무 규칙 / 선택한 구조·알고리즘 / 더 단순한 대안 / 예상 비용 / 실패할 수 있는 입력 / 검증 방법을 기록한다.

예: ‘ID 중복 확인을 위해 Map을 쓴다’에서 끝내지 말고 동일 ID·동일 내용은 합칠지, 다른 내용은 오류인지, 어떤 입력으로 확인할지까지 연결한다. 정책의 출처가 없으면 질문 또는 가정으로 남긴다.
