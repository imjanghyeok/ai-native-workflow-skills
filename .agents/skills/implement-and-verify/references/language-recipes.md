# 문법을 작업별 레시피로 준비하기

과제 언어와 런타임이 아직 정해지지 않았다면 여러 언어의 긴 문법 사전을 만들지 않는다. 먼저 프로젝트·버전·의존성·기존 관례를 확인하고, 실제 필요한 작업의 작은 예제를 찾아 쓰거나 작성한다. 제공 Codex·터미널과 허용된 자료 접근 방식을 따른다.

## 언어가 정해진 뒤 채울 레시피 목록

| 필요한 작업 | 예제에서 꼭 확인할 것 |
| --- | --- |
| 파일·CSV·JSON 읽고 쓰기 | 인코딩, 헤더, 빈 입력, 파싱 실패, 실제 저장 여부 |
| 숫자·문자열·날짜 변환 | 잘못된 값, 공백, 0·음수, 단위, 시간대, 날짜 경계 |
| Map/Set 조회·그룹 집계 | 키 동등성, 없는 키, 복합 키 충돌, 누락과 0 구분 |
| 정렬·필터·상위 항목 | 숫자 비교, 동률, 원본 변경 여부, 빈 결과 |
| 입력 검증·예외 처리 | 언어의 오류 전파 방식, 프로젝트의 응답·오류 계약 |
| 함수·모듈·타입 정의 | 기존 버전에서 지원하는 문법, import·실행 위치, 타입·스키마 |
| API 요청·서버 처리 | 실제 사용 프레임워크, 상태 코드, 실패·타임아웃·중복 요청 |
| 테스트·디버깅 | 프로젝트의 실행 명령, fixture, 실제 실패 메시지, 재현 입력 |

API·라이브러리 예제는 설치된 버전과 공식 문서를 확인한다. 기억만으로 존재하지 않는 함수·옵션을 만들지 않는다. 기존 코드에 같은 작업이 있으면 먼저 읽고 활용한다.

## 각 레시피의 최소 형태

- 적용 언어·버전과 필요한 의존성.
- 해결할 작은 작업과 출처.
- 실행 가능한 짧은 코드, 입력, 기대 결과.
- 정상 입력과 해당 작업에 중요한 실패/경계 입력.
- 실제 실행 명령·결과 또는 ‘미실행’ 표시.
- 원본을 변경하는지, 오류가 어떻게 전달되는지, 지원하지 않는 범위.

짧은 예제는 표준 라이브러리나 기존 의존성을 우선한다. 외부 서비스에 접근하는 예제에는 실제 키나 시험 데이터를 넣지 않는다. 문법 확인용 코드를 제품 코드에 남겨 실행 경로를 바꾸지 않는다.

## 실행으로 확인할 언어별 차이

변수·리스트·함수 문법만 보고 옮겨 쓰지 말고 다음의 의미 차이를 확인한다:

- truthy/falsy 판단으로 정상적인 0·빈 문자열을 누락으로 오해하지 않는가?
- 정렬의 기본 기준·비교 함수·원본 변경 여부가 의도와 맞는가?
- 객체·리스트 복사가 얕은 복사인지, 원본의 중첩 데이터를 바꾸는가?
- 날짜의 파싱·지역 시간대·종료일 포함 처리가 일치하는가?
- 부동소수점 오차·정수 범위·나눗셈·반올림이 업무 규칙에 맞는가?
- 비동기 작업 완료를 기다리고 실제 저장·요청 실패를 처리하는가?

필요한 레시피만 그때 읽고 적용한다. 예제 코드가 실행된 사실과 현재 과제의 요구를 만족한다는 사실을 별도로 검증한다.
