# 요청을 코드까지 따라가기

핵심 흐름을 한 개 고르고 진입점부터 최종 효과까지 따라간다. 경로를 모르면 테스트·핸들러 등록·클라이언트 호출을 찾아 서로 대조한다. 코드만 읽었다면 정적 추적, 실제 명령/입력을 넣었다면 실행 확인으로 구분한다.

| 흐름 단계 | 실제 코드/심볼 | 입력·출력 | 책임/권한/실패 | 근거 상태 |
| --- | --- | --- | --- | --- |

API 표는 실제 method/path 또는 CLI/이벤트 계약을 사용한다. 주체·권한 조건, 스키마/ID/단위/null, 호출 모듈, 저장 효과, 응답·오류와 테스트를 연결한다. 요구에 없는 API를 문서에 발명하지 않는다. 전체 API 목록이 필요하면 실제 등록 경로와 누락을 대조한다.

데이터 흐름에는 원본 → 파싱/정제 → 도메인 객체 → 저장/집계 → 응답/화면을 구분한다. 각 변환에서 어떤 ID와 단위를 유지하고 누가 데이터를 변경하는지 적는다. 객체 관계는 코드의 실제 필드/메서드와 생명주기로 설명한다. 실제 저장이 없으면 `메모리 상태`로 쓴다.

디버깅 자료는 증상 → 재현 입력 → 관찰 지점 → 예상 계약 → 실제 어긋남 → 관련 테스트를 잇는다. 네트워크 실패, 인가 거절, 입력 오류, 저장 실패가 있다면 어느 경계에서 변환/전파되는지 보여준다. 확인하지 않은 원인을 단정하지 않는다.

설명 연습에서는 사용자가 말한 흐름을 실제 코드와 대조한다. `이 요청은 어디에서 검증되는가`, `이 모듈이 실패하면 무엇이 바뀌는가`, `이 의존성을 제거하면 어떤 경로가 끊기는가` 같은 질문을 실제 자료에서 생성한다. 모범 응답을 사용자의 이해 증명으로 쓰지 않는다.


공통 오류/권한 정책은 한 핸들러의 설명만으로 전체 구현을 확정하지 않는다. 라우터의 정상 일치·미일치/폴백·정적 제공·예외 변환 경로도 실제 코드와 대조한다. 권한 검사와 식별자/본문 검증의 순서가 계약과 같은지 확인한다. 흐름 그림에서 누락한 경계가 발견되면 관련 재현 입력과 소유 일감으로 연결한다.

## 기능·코드·실제 확인을 한 표로 연결

주요 기능에 대해서만 기존 코드맵/검증 문서에 아래 연결을 만든다. API/저장/권한이 없는 기능에 그 계층을 만들어 넣지 않는다. 실제 관찰과 사용자 확인이 없는 값을 채웠다고 쓰지 않는다.

| 기능/요구ID | 동작 입력·사용 순서 | 실제 파일·심볼/책임·연결 흐름 | 확인 방법·기대 결과 | 관찰 결과·근거/주체 | 미확인·한계 |
| --- | --- | --- | --- | --- | --- |

코드를 정적으로 따라 읽은 근거, 실제 명령/테스트/HTTP 응답, 제공 미리보기에서 사용자가 확인한 UI를 구분한다. 관련 정상·실패·저장 후 재조회 중 실제 수행 범위와 코드 상태를 연결한다. 확인 주체는AI직접실행/사용자직접확인/인계받은관찰 등으로 분리하고 날짜/명령/입력/출력·로그를 필요한 수준으로 남긴다.

작업 단계의 종료 인계는 무엇을 구현했는지→사용자가 어떻게 동작시키는지→어떤 코드가 처리하는지→어떻게 확인했는지→남은 한계를 실제 근거로 짧게 정리한다. 이는 허용된 작업/연습 중 이해 자료이며 실제 시험 문항·정답을 재구성하거나 본인 답변을 대신 작성하는 양식이 아니다. AI·복사/붙여넣기 금지 후속 단계에 AI나 자료 열람이 허용된다고 가정하지 않는다.
