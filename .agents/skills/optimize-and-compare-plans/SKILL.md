# 목표·제약에서 실행 가능한 운영안 비교까지

## 1. 모델을 결정하기 전에

원문 요구ID·기존 데이터/분석·현재 운영/실행 계약을 읽는다. 수요·작업량이 입력이면 demand-and-workload-analysis의 정의/출처/기간을 재사용한다. 결정변수(바꿀 값), 입력(주어진 값), 파생 지표, 사용자/현업 정책을 구분한다. 자료에 없는 정책을 정답으로 만들지 않는다.

필수 제약에는 단위/범위·경계 포함·검사 방법을 붙인다. 조건에 해당하면 용량·동시 점유·가용시간·선행관계·배정 적격성·연속성·전환/재사용 비용을 표현한다. 소프트 선호/비용을 필수 제약과 분리하고, 실패 후보가 높은 점수로 채택되지 않게 한다. 부분 처리를 허용하는지 원문으로 확인하며 미처리 수요를 숨기지 않는다.

목적의 최소/최대 방향·단위·집계대상·가중치/우선순위·분모를 명시한다. 단위가 다른 값을 그대로 더하지 않는다. 가중치가 미정이면 가정/선택지 또는 다목적 절충 후보로 제시하고 AI 임의값을 공식 기준으로 쓰지 않는다. 필수 정확성·업무 의미가 바뀌는 선택만 판단 대기로 올린다.

## 2. 기준안과 알고리즘

먼저 단순 기준안과 독립 제약 검사/목적 계산을 준비한다. 기존 운영안은 위반이 있어도 사실대로 비교 대상으로 남기되 실행 가능한 추천으로 채택하지 않는다. 가능한 기준안이 없으면 없다고 쓰고 불가능/미탐색을 구분한다. [알고리즘·비교 기준](references/methods-and-evaluation.md)을 입력 크기/구조/시간/정확성에 맞게 선택한다.

Sol은 모델·정책·검증 기준을 정리하고 Terra에 명확한 TODO/계약/소유 파일/정상·실패·경계 기대값을 넘긴다. 큰 최적화 라이브러리·외부API·Python을 기본 설치하지 않는다. 기존 JS/TS/도구에서 충분한 기준안/탐욕/작은 탐색을 먼저 검토한다. 시간 제한과 검증/제출 예산은 task-triage의 time-budget 기준을 따르며 항상 최적해를 보장한다고 쓰지 않는다.

## 3. 같은 조건으로 후보 검증

수요·데이터/설정 버전·자원·기간·미처리 규칙을 고정하고 기준안/후보를 같은 평가기로 재계산한다. 점수 전에 원문 필수 제약·누락/중복 배정·용량·일정 중 실제 관련 위반을 별도 확인한다. 후보 생성 함수의 성공 표시만으로 유효성을 판단하지 않는다. 제약 허용오차는 단위/이유를 밝히고 출력 반올림/정규화 후에도 다시 확인한다.

실행 가능한 후보끼리 목적·서비스/품질·자원/비용·집단별 영향과 남은 한계를 비교한다. 실행 불가안은 위반과 참고 지표를 따로 표기하고 추천/최적해로 선택하지 않는다. 평균 개선과 함께 관련 최대/분위수/미충족·불이익 집단을 확인한다. 최적안이 여러 목적에서 서로 우열이 갈리면 절충을 보여주고 선택 책임을 남긴다.

## 4. 검증·선택·한계

관련 작은 입력의 수동/완전탐색 정답,0수요/0자원·동률·해 없음·순서 변경·용량 경계 등 실제 위험을 고른다. 확률/휴리스틱이면 seed·버전·실행 예산을 남기며 한 번의 좋은 결과를 일반 보장으로 쓰지 않는다. 요구에 관련된 수요/처리시간/비용의 변화 시나리오와 선택 가중치 민감도를 명시해 결론이 바뀌는지 확인한다.

탐색 중단/시간 초과로 해를 못 찾음은 수학적 불가능 증명이 아니다. 실행가능·최적성 증명·허용 gap·시간제한·미탐색/실패 상태를 구분한다. 절감률 분모0·서로 다른 평가기간·누락 수요/비용·숨은 용량 위반을 검증한다. 작은 완전탐색의 최적성은 그 작은 입력에만 해당한다.

기존 설계/검증 문서에 모델/정책·기준안·후보별 제약 위반/지표·실제 명령/결과·선택/거절 이유·조건/한계를 연결한다. 자료구조/알고리즘 책임과 평가기/설정 의존성은 code-to-system-map으로 실제 코드에 연결한다. 문서/스킬이 존재하는 것과 실제 구현/검증 완료는 별개다.
