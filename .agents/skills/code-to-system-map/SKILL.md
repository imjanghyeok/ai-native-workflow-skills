# 구현에서 설명 가능한 시스템 지도로

코드 분석 요청은 코드 수정 권한이 아니다. 실제 엔트리·설정·호출부·저장소·테스트를 근거로 작성하고 계획/관찰/실행 확인/미확인을 구분한다. 전 코드를 이해했다는 선언이나 예상 후속 질문의 정답을 만들어주지 않는다.

분석 전용이면 원본 과제 README·AGENTS·입력·코드·테스트를 읽기 자료로 보존한다. 분석을 명확하게 설명하려고 원문에 조건/주석을 덧붙이지 말고 허용된 출력 문서에 해석·출처를 적는다. 사용자가 명시한 출력 경로만 수정하며 원문 자체 수정을 요청한 경우와 구분한다.

## 조사 범위

1. 사용자 관심 흐름과 원문 요구를 찾고 실제 revision/파일 집합을 식별한다. 폴더 목록만으로 책임을 추정하지 않는다. 엔트리·라우트·핸들러·서비스·저장소·화면 호출부·테스트를 작은 범위부터 따라간다.
2. [아키텍처·의존성 추적](references/architecture-and-dependencies.md)에 따라 논리 모듈, 실제 프로세스/배포 단위, 라이브러리와 외부 서비스를 구분한다. 하나의 프로세스를 임의의 마이크로서비스로 그리지 않는다.
3. 코드에서 확인한 책임·권한 검사·데이터 변경 위치를 파일/심볼 링크와 연결한다. 검사가 없거나 가정이면 그대로 표시한다. 인증과 인가, 화면 표시 제한과 서버 통제는 구분한다.
4. [흐름·근거·디버깅](references/flows-and-evidence.md)에 따라 핵심 요청의 정상/실패 경로와 역방향 추적법을 만든다. 실제 호출하지 않은 경로는 정적 추적이라고 적는다.

## 작은 자료부터

기존 설계/검증 문서에 합칠 수 있다. 크기가 필요하면 `docs/code-map.md`를 진입점으로 하고 API/데이터 흐름·배포 구성은 링크로 분리한다. 범용 [코드맵 양식](../../../templates/CODE-MAP.md)은 선택 사항이다. 함수 하나마다 문서를 늘리지 않는다.

- 모듈 표: R-ID → 실제 파일·심볼 → 책임/소유 상태 → 입력/출력 → 호출·의존 → 권한·오류 → 검증 근거.
- 아키텍처 그림: 사용자/외부 입력, 실제 실행 단위, 데이터 저장소·외부 경계. `관찰된 현재 구조`와 `제안·미구현`을 명확히 나눈다.
- 기능 근거 표: 주요 기능의 사용 입력/순서 → 실제 코드 책임/연결 → 확인 방법/기대·관찰 결과 → 확인 주체·미확인. [흐름·근거](references/flows-and-evidence.md)의 양식을 필요한 기능만 기존 문서에 합친다.
- 대표 흐름: 요청/이벤트 → 검증/인가 → 업무 판단 → 읽기·변경/트랜잭션 → 응답·오류. 사용자 역할이 없는 코드에 역할을 추가하지 않는다.
- 의존성 표: 직접/간접/런타임/빌드·개발·외부 서비스, 실제 버전 근거, 사용 모듈·용도, 장애/교체 영향, 확인 한계.

Mermaid 구문이 필요할 때만 [선별 문법 참고](references/mermaid-reference.md)를 읽는다. 기존 프로젝트의 렌더러가 있으면 로컬로 확인하고, 없으면 문법 원문·동등한 표·미렌더 상태를 남긴다. 시험 코드/그림을 외부 Mermaid 편집기·문서 서비스에 보내지 않는다. 문서 작성을 위해 브라우저 자동 조작이나 새 MCP를 추가하지 않는다.

## 완료 기준

주요 노드/화살표마다 실제 파일·심볼 근거가 있는지 확인한다. 정적 의존만으로 런타임 호출을 확정하지 않는다. 코드 변경으로 문서가 달라진 지점을 갱신하고 기준 상태·확인 범위를 적는다. 사용자에게 한 요청을 직접 따라 설명하거나 특정 모듈 변경의 영향을 짚게 해 이해를 확인하되 답을 대신 본인 경험으로 쓰지 않는다.
