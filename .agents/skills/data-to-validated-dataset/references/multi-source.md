# 여러 파일 결합에서 확인할 불변 조건

## 행 의미와 키를 먼저 구분

생산 CSV의 한 행은 배치, JSON의 한 객체는 설비, 로그 한 행은 이벤트일 수 있다. 설비 ID가 같다는 사실만으로 행끼리 일대일 대응하지 않는다. 설비 정보의 유일성이 필요한 설계에서는 중복 키를 검사하고, 계약에 없는 ‘마지막 값 우선’ dict 변환으로 충돌을 감추지 않는다.

생산 2배치와 알람 2이벤트를 직접 연결하면 4행이 된다. 원하는 결과가 날짜·설비별 합계라면 두 사실 자료를 해당 단위로 각각 집계한 뒤 연결하는 방법을 검토한다. 필요한 출력이 이벤트 상세라면 생산 수량 반복 표시는 가능해도 반복값의 합산이 적절한지는 별도 계약이다.

## 시간대와 동일성

- 날짜 키를 만들기 **전에** 계약의 업무 시간대로 변환한다. 예를 들어 UTC+09:00 기준에서 10월 29일 15:00Z는 10월 30일이다. 날짜 문자열을 먼저 자르면 다른 날짜 생산과 연결될 수 있다.
- 같은 시각이 Z와 +09:00으로 다르게 적혀도 동일 이벤트일 수 있다. 중복 비교는 계약에 맞는 정규화 시각을 쓰되 원본 시각·위치를 보존한다.
- 파서가 성공했다고 입력 형식이 계약을 지킨 것은 아니다. 오프셋·필수 시간대·초 정밀도 같은 조건이 있다면 따로 확인한다. 실제 Python 실행에서 +09:99가 +10:39로 해석된 사례처럼 관대한 파서가 잘못된 값을 정상화할 수 있다. 사용하는 런타임에서 경계 입력을 직접 시험한다.

## 미매칭을 하나로 뭉치지 않기

설비 JSON에 이름이 없는 생산과, 해당 날짜에 생산이 없는 알람은 서로 다른 문제다. 기준 행을 남길지 제외할지, 어느 합계에 넣을지 실제 계약에 따라 구분한다. 같은 설비에 다른 날짜 생산이 있다는 이유로 로그를 임의의 날짜에 붙이지 않는다.

## 건수와 합계 대조

상충 ID가 1개이고 그 ID에 정상 원본 행이 3개라면 ‘상충 키 1개’와 ‘상충 제외 행 3개’를 나눈다. raw=invalid+duplicate+conflict+accepted 같은 식은 **같은 단계의 상호 배타적인 행 분류**일 때만 사용한다. 대표 채택 행과 추가 중복 행을 분리하고, 충돌 그룹을 duplicate와 다시 이중 계산하지 않는다.

미매칭은 유효성 검사 이후 분류일 수 있다. 이 경우 accepted=matched+unmatched와 함께, 알람 초처럼 수량도 accepted_seconds=matched_seconds+unmatched_seconds로 대조한다. 출력 기준에 없는 유효 데이터가 사라지는 것을 총합 불일치로 드러낼 수 있다.

## 재실행과 실패

원본·출력의 경로를 구분하고 원본 해시와 최종 결과 재읽기를 확인한다. 기본적으로 기존 결과를 보호하는 CLI라면 재실행도 명시적 교체 옵션 또는 새 출력 경로를 써야 한다. 같은 입력의 명시적 재실행이 같은 의미의 결과를 내는지, 잘못된 입력으로 실패할 때 이전 정상 출력이 남는지 검증한다. 산출물 형식이 불안정한 실행시각을 포함하면 바이트 동일성이 아닌 계약상 같은 내용을 대조한다.
